Fluxion 内存泄漏风险核查报告
日期：2026-06-17
范围：src/core、src/common、tests/e2e 运行时用法、README 中的运行时选项说明

概要
- 总体风险：中等。
- 框架核心代码里没有发现明显的 native buffer 泄漏，也没有发现持续增长的全局数组。
- 主要风险来自动态路由模块缺少生命周期清理、请求执行缺少上限控制、worker 防护选项未实际生效，以及少量 stream/watch 边界场景。

问题清单

1. 【已解决】高风险 - 动态 handler 热重载缺少 dispose/teardown 清理路径
- 证据：
  - src/core/router.ts:78 只执行了 delete require.cache[fullpath]。
  - src/core/router.ts:92-94 加载新 handler，并替换 router Map 中的旧 handler。
  - src/common/injector.ts:4 使用 require(modulePath) 加载模块，但没有卸载生命周期。
- 风险：
  - 如果动态 handler 模块在顶层创建 interval、socket、数据库连接池、文件 watcher、大型模块缓存或事件监听器，每次热重载都可能创建一份新资源，而旧资源仍然存活。
  - 替换 handlers Map 中的函数引用，只能释放旧函数引用本身，不能停止旧模块创建的副作用资源。
  - 只删除直接模块的 require.cache，也不会清理 handler 引入的子模块；子模块状态和缓存可能继续保留。
- 建议：
  - 增加可选模块生命周期，例如 export function dispose()，在替换或删除 handler 前调用。
  - 按路由记录已加载模块信息，并使用 require.resolve(fullpath) 作为 cache key。
  - 考虑递归清理 dynamic directory 下的子模块 require.cache；或者明确文档约束：热重载 handler 不应在模块顶层创建持久资源，除非同时提供 dispose()。

1. 【已解决】高风险 - 请求 handler 缺少超时控制，卡住的 handler 会长期持有上下文
- 证据：
  - src/core/cluster/server.ts:85 直接 await PromiseTry(handler, normalized, req, res)。
  - src/core/utils/options.ts:14 定义了 workerOptions.requestTimeoutMs，但运行时代码没有引用。
  - rg 搜索显示 requestTimeoutMs 只出现在 types/options/README 中，没有参与 server 执行逻辑。
- 风险：
  - handler 如果永不 resolve、等待失效上游服务，或留下 pending Promise，会持续持有 normalized request、raw req/res、body buffer、闭包和 finish listener 状态。
  - 在重复请求下，这会变成应用层内存泄漏或资源泄漏。
- 建议：
  - 用 AbortController/timeout race 包装 handler 执行。
  - 超时后尽可能返回 504/503，并安全地 destroy 或 drain request/response。
  - 将 AbortSignal 传给 handler，让业务代码可以取消下游操作。

1. 高风险 - 声明的 worker 内存/并发保护选项没有实际执行
- 证据：
  - src/core/utils/options.ts:14-22 定义 requestTimeoutMs、maxInflight、memorySoftLimitMb、memoryHardLimitMb、memorySampleIntervalMs、maxOldGenerationSizeMb、maxYoungGenerationSizeMb、stackSizeMb、maxResponseBytes。
  - rg 显示这些选项除 options/types/README 外基本未被消费；当前只看到 telemetry 上报。
  - src/core/cluster/worker.ts:24-62 只上报内存状态，没有重启、限流或熔断逻辑。
- 风险：
  - 框架声明了防护能力，但运行时没有执行；发生 handler 泄漏时，进程会持续增长直到进程或系统限制触发。
  - maxInflight 未使用意味着 worker 会接受无限并发的 handler 执行，慢请求或卡住请求会成倍放大 retained request/body 对象。
- 建议：
  - 在 createWorkerServer 中，在 parseBody/handler 执行前强制执行 maxInflight。
  - 同步落实 requestTimeoutMs。
  - 增加 worker 内存监控：达到 hard limit 时退出/重启 worker；达到 soft limit 时在空闲时 drain/recycle。
  - 如果这些 V8 配置选项确实要生效，在 cluster.fork 时应用对应 execArgv 限制。

1. 中风险 - 静态文件流在客户端中断时可能留下 pending Promise
- 证据：
  - src/core/router.ts:55-60 创建 ReadStream，只在 stream 'end' 时 resolve，在 stream 'error' 时 reject。
  - 没有监听 res 'close'、req 'aborted' 或 stream 'close'。
- 风险：
  - 如果客户端在静态文件传输中途断开，ReadStream/pipe 可能 close 但不经过 'end' resolve。
  - async 请求处理可能一直 pending，并继续持有 req、res、stream、normalized request 数据和 logger 闭包。
- 建议：
  - 监听 res.close 和 req.aborted，销毁 stream，并保证 Promise 只 settle 一次。
  - cleanup 时移除相关 listener。

1. 中风险 - 删除整个目录时，router Map 中可能残留旧 API handler
- 证据：
  - src/core/watch.ts:60-70 从 fs.watch 获取 filename 后调用 router.register(filename)。
  - src/core/router.ts:72-75 在路径不存在时只删除精确 filepath key。
  - src/core/router.ts:14 使用 Map 按 route path 存储 handler。
- 风险：
  - 如果删除一个包含 API 文件的目录，而 fs.watch 只上报目录路径，子路由条目可能仍留在 handlers Map 中。
  - 残留 handler 会继续持有旧函数闭包和其中捕获的模块状态。
  - 这同时也是正确性问题：已删除 API 可能仍然可被访问。
- 建议：
  - 当删除路径是目录或路径前缀时，删除该前缀下所有 handler key。
  - 在 rename/delete 事件上执行全量重扫，或周期性将 handlers Map 与文件系统状态做 reconciliation。

1. 中风险 - Fluxion runtime 没有公开 stop/dispose 生命周期
- 证据：
  - src/core/fluxion.ts:11-25 启动 primary 或 worker，但不返回任何 handle。
  - src/core/cluster/primary.ts:73 启动 meta API server，src/core/cluster/primary.ts:133 创建 pingTimer。
  - src/core/cluster/worker.ts:69 添加 process message listener，src/core/cluster/worker.ts:81 启动 stats interval。
  - src/core/cluster/server.ts:16 创建 business server；initWorker 没有保存或返回该 server。
- 风险：
  - 在测试、嵌入式运行、热重启，或同一进程内重复调用 fluxion() 时，server、interval、watcher 和 process listener 可能累积。
  - pingTimer/stats interval 使用了 unref()，这有助于进程退出，但进程继续运行时 unref() 不会释放其捕获状态。
- 建议：
  - 让 fluxion() 返回生命周期 handle，例如 close()/dispose()。
  - dispose 时清理 interval、关闭 server/watcher，并移除 process/worker listener。
  - 防止同一进程重复 start，或明确文档说明该 runtime 是一次性进程模型。

1. 中风险 - FluxionWatcher.start() 非幂等，重复调用会泄漏旧 watcher
- 证据：
  - src/core/watch.ts:57-90 直接 this.watcher = fs.watch(...)，创建新 watcher 前没有关闭旧 watcher。
  - src/core/watch.ts:92-105 有 stop()，但 start() 没有调用 stop()。
- 风险：
  - 如果外部直接重复调用 start()，旧 FSWatcher 会被 this.watcher 覆盖，之后不再可达，也无法 close。
  - 当前框架路径只启动一次，错误重启也使用 stop().start()，所以这主要是 API 误用风险。
- 建议：
  - start() 创建新 watcher 前先调用 this.stop()，或者在已启动时直接抛错。

1. 中风险 - 带 Content-Length 的超大请求在未 drain/destroy request 前就被拒绝
- 证据：
  - src/core/utils/body.ts:82-87 检查 content-length 后直接抛 REQUEST_BODY_TOO_LARGE。
  - src/core/cluster/server.ts:98-101 返回 413，但没有 drain 或 destroy request。
  - chunked 超限请求在 src/core/utils/body.ts:117-121 中有 cleanup() 和 req.resume()，处理方式不同。
- 风险：
  - 如果客户端声明了超大 body 且继续发送数据，server 在返回 413 后仍可能占用 socket/parser 资源。
  - 这更偏向资源耗尽风险，不是典型的长期 heap 泄漏，但在攻击流量下会造成内存和连接压力。
- 建议：
  - 对声明超大的请求，在返回 413 后根据 keep-alive 策略调用 req.resume() 或销毁 request/socket。
  - 让 content-length 分支与 chunked 超限分支的资源处理保持一致。

1. 低风险 - 请求 body parser 会按设计缓存完整的已接受 body
- 证据：
  - src/core/utils/body.ts:90 保存 rawBodyChunks。
  - src/core/utils/body.ts:145 将完整 raw body Buffer.concat。
  - src/core/utils/options.ts:50 默认 maxRequestBytes 为 8_000_000。
- 风险：
  - 这本身不是泄漏，但每个并发请求在 handler 内存之外，最多可能占用接近 maxRequestBytes 的 body 内存。
  - 因为 maxInflight 尚未执行，高并发下这个问题会被放大。
- 建议：
  - 执行 maxInflight。
  - 对大文件上传提供 streaming API，或在资源受限部署中降低默认 maxRequestBytes。

1.  低风险 - Router handler Map 只受 dynamic directory 文件数量约束
- 证据：
  - src/core/router.ts:14 创建 handlers Map。
  - src/core/watch.ts:23-43 递归注册所有文件。
- 风险：
  - 这是文件系统路由的预期行为，但如果 dynamic directory 被当作无限上传目录使用，route/static handler 条目也会无上限增长。
  - 如果删除事件遗漏，上述目录删除残留问题会进一步放大该风险。
- 建议：
  - 文档明确说明 dir 不应直接作为无限上传目录，除非合理配置 routerExclude/apiExts。
  - 增加可选 route 数量上限，或加入文件系统 reconciliation。

正向检查结果
- src/core/utils/body.ts 在 chunked body 正常结束、错误、abort 或运行中超限时，会移除 data/end/error/aborted listener。
- src/core/watch.ts 的 stop() 会关闭当前 FSWatcher、清除 debounce timer，并清空 filesChanged。
- src/core/cluster/primary.ts 在 worker exit 时会从 workers Map 删除对应 worker。
- src/core/cluster/worker.ts 和 src/core/cluster/primary.ts 使用了 interval.unref()/pingTimer.unref()；这有助于进程退出，但不能替代显式清理。
- src/core/utils/query.ts、cookie.ts、headers.ts、request.ts、respond.ts 没有保留持久化的进程级容器。

建议修复顺序
1. 在 router reload/removal 中实现 handler/module dispose，并修正 require.cache 处理方式。
2. 在 createWorkerServer 中执行 requestTimeoutMs 和 maxInflight。
3. 增加 worker 内存 hard-limit recycle/restart 逻辑；如果暂不实现，则移除或修正文档中未生效的选项说明。
4. 修复静态文件流在 abort/close 场景下的 settle 和 cleanup。
5. 增加 runtime dispose handle，并让 watcher start 幂等。
6. 补充测试：热重载清理、卡住 handler 超时、静态文件传输中断、超大 Content-Length、目录删除 reconciliation。

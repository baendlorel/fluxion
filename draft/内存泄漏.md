Fluxion 内存泄漏风险核查报告
日期：2026-06-17
范围：src/core、src/common、tests/e2e 运行时用法、README 中的运行时选项说明

概要（2026-06-24 更新）
- 总体风险：**中等偏低**（较之前有改善）。
- **已解决的重要问题**: 请求 handler 超时控制已实现、watcher 非幂等问题已修复、worker 内存/健康检查保护已实现。
- **仍存在的主要风险**: maxInflight 并发控制仍未实现（高优先级）、静态文件流客户端中断处理缺失、目录删除时路由残留问题、Content-Length 超限请求资源处理不一致。
- **新的积极发现**: 代码结构重组更加清晰，模块化更好，生命周期管理有显著改善。

问题清单

1. 【部分修复】高风险 - 动态 handler 热重载缺少 dispose/teardown 清理路径
- **当前状态**: 已添加 disposer 支持，但子模块清理仍不完整
- **修复证据**:
  - src/router/index.ts:73-75 现在会调用 disposer：`const disposer = this.handlers.get(relativePath)?.disposer; if (disposer) { await PromiseTry(disposer); }`
  - 框架现在支持模块导出 `disposer` 函数进行清理
- **遗留问题**:
  - src/common/injector.ts:40 仍然只执行 `delete require.cache[fullpath]`，没有递归清理子模块的 require.cache
  - 如果 handler 引入的子模块创建了全局资源（interval、socket、数据库连接池），这些资源可能无法被清理
- **进一步修复建议**:
  - 实现 `require.resolve()` 递归清理子模块 require.cache
  - 或在文档中明确约束：热重载 handler 不应在模块顶层或引入的子模块中创建持久资源，除非提供 dispose() 清理函数

1. ✅ **已完全解决** - 请求 handler 缺少超时控制，卡住的 handler 会长期持有上下文
- **修复证据**:
  - src/cluster/server.ts:24-25 实现了 `waiter` 函数：`const waiter = (mainPromise: Promise<any>, timeoutMs: number, flag: symbol) => Promise.race([mainPromise, new Promise((r) => setTimeout(() => r(flag), timeoutMs))]);`
  - src/cluster/server.ts:105-108 配置超时：`const timeoutMs = m.type === FluxionModuleType.Api ? (m.handlerTimeoutMs ?? cx.options.handlerTimeoutMs) : cx.options.staticResourceTimeoutMs;`
  - src/cluster/server.ts:113-127 middleware 超时控制：使用 `MIDDLEWARE_TIMEOUT_FLAG` 和 `middlewareTimeoutMs`
  - src/cluster/server.ts:138-148 handler 超时控制：使用 `HANDLER_TIMEOUT_FLAG` 和配置的 timeout
  - src/http/options.ts:98-100 定义了 `handlerTimeoutMs = 5000, middlewareTimeoutMs = 3000, staticResourceTimeoutMs = 10 * 600000`
- **验证**: ✅ 超时机制已完整实现，包括 middleware 和 handler 的超时控制，超时后会返回 500 错误并记录日志

1. 【部分修复】高风险 - 声明的 worker 内存/并发保护选项没有实际执行
- **当前状态**: 内存和健康检查已实现，但并发控制（maxInflight）仍未实现
- **修复证据**:
  - src/http/options.ts:10-26 正确定义了 workerOptions：`maxWorkerCount、restartWhen.memoryUsageGreaterThan、restartWhen.healthzTimeout、restartWhen.uptimeGreaterThan`
  - src/cluster/primary.ts:168-181 实现了 `evaluateResourceConditions` 函数，检查内存和运行时间并触发重启
  - src/cluster/primary.ts:185-196 实现了 `evaluateLiveness` 函数，检查 healthzTimeout 并触发重启
  - src/cluster/primary.ts:138-163 实现了 `initiateRecycle` 函数，包含防风暴机制（anti-storm）和重启逻辑
  - src/cluster/primary.ts:18-21 实现了防风暴保护：`RESTART_WINDOW_MS = 60_000, MAX_RESTARTS_PER_WINDOW = 3`
- **遗留问题**:
  - **maxInflight 并发控制仍未实现** - 这是高风险项，慢请求或卡住的请求会成倍放大 retained request/body 对象
  - 没有在 createWorkerServer 中实现并发请求上限控制
- **进一步修复建议**:
  - **高优先级**: 实现 maxInflight 并发控制，在 parseBody/handler 执行前检查当前并发请求数
  - 可以使用简单的计数器或信号量模式来限制并发请求数
  - 当达到上限时，应该返回 503 Service Unavailable 或排队等待

1. ⚠️ **仍未解决** - 中风险 - 静态文件流在客户端中断时可能留下 pending Promise
- **当前状态**: 问题仍然存在
- **证据**:
  - src/router/index.ts:53-58 创建 ReadStream，只在 stream 'end' 时 resolve，在 stream 'error' 时 reject
  - 没有监听 res 'close'、req 'aborted' 或 stream 'close' 事件
- **风险**:
  - 如果客户端在静态文件传输中途断开连接，ReadStream/pipe 可能 close 但不经过 'end' resolve
  - async 请求处理可能一直 pending，并继续持有 req、res、stream、normalized request 数据和 logger 闭包
- **修复建议**:
  - 监听 `res.on('close')` 和 `req.on('aborted')` 事件
  - 在客户端断开时销毁 stream 并 resolve Promise（只 settle 一次）
  - 在 cleanup 时移除相关 listener
  - 可以参考 src/http/body.ts:94-99 的 cleanup 模式实现

1. ⚠️ **仍未解决** - 中风险 - 删除整个目录时，router Map 中可能残留旧 API handler
- **当前状态**: 问题仍然存在
- **证据**:
  - src/router/index.ts:72-83 在路径不存在时只执行 `this.handlers.delete(relativePath)`，删除精确 filepath key
  - src/router/index.ts:11 使用 Map 按 route path 存储 handler
  - src/watcher/chokidar.ts:37-44 和 src/watcher/native.ts:24-31 都只是简单地调用 `this.queueUp()` 处理单个文件
- **风险**:
  - 如果删除一个包含 API 文件的目录，子路由条目可能仍留在 handlers Map 中
  - 残留 handler 会继续持有旧函数闭包和其中捕获的模块状态
  - 这同时也是正确性问题：已删除 API 可能仍然可被访问
- **修复建议**:
  - 在删除事件中检测是否为目录，如果是目录则删除该前缀下所有 handler key
  - 或者定期执行 reconciliation，将 handlers Map 与文件系统状态对比
  - 可以在 watcher 中增加对目录删除事件的特殊处理，递归删除所有相关路由

1. 【部分修复】中风险 - Fluxion runtime 没有公开 stop/dispose 生命周期
- **当前状态**: 有部分清理机制，但仍未公开完整的 dispose API
- **修复证据**:
  - src/cluster/worker.ts:84-105 实现了 `shutdown` 函数，处理 SIGINT/SIGTERM 信号
  - src/cluster/worker.ts:90 调用 `cx.watcher.stop()` 进行清理
  - src/cluster/worker.ts:96-104 调用 `server.close()` 关闭服务器
  - src/watcher/chokidar.ts:59-67 和 src/watcher/native.ts:42-50 都实现了 `stop()` 方法
  - src/cluster/primary.ts:328 的 pingTimer 使用了 `unref()`
- **遗留问题**:
  - src/fluxion.ts:12-28 的 `fluxion()` 函数仍然不返回任何 handle，无法主动清理
  - 在测试、嵌入式运行场景中，无法显式关闭和清理资源
  - 重复调用 fluxion() 仍可能造成资源累积
- **进一步修复建议**:
  - 让 `fluxion()` 返回一个包含 `dispose()` 或 `close()` 方法的对象
  - dispose 时应该清理 interval、关闭 server/watcher、移除 process listener
  - 或者明确文档说明该 runtime 是一次性进程模型，不支持重复调用

1. ✅ **已完全解决** - 中风险 - FluxionWatcher.start() 非幂等，重复调用会泄漏旧 watcher
- **修复证据**:
  - src/watcher/chokidar.ts:22-24 在 `start()` 方法开始时调用 `this.stop()`：`async start(): Promise<this> { this.stop(); await this.init(); ... }`
  - src/watcher/native.ts:18-20 同样在 `start()` 方法开始时调用 `this.stop()`：`async start(): Promise<this> { this.stop(); await this.init(); ... }`
  - 两个实现都会在创建新 watcher 前先关闭旧 watcher
  - src/watcher/chokidar.ts:59-67 和 src/watcher/native.ts:42-50 都正确实现了 `stop()` 方法
- **验证**: ✅ 现在调用 `start()` 会先调用 `stop()`，确保旧的 watcher 被正确关闭，不会泄漏 FSWatcher 资源

1. ⚠️ **部分改善** - 中风险 - 带 Content-Length 的超大请求在未 drain/destroy request 前就被拒绝
- **当前状态**: chunked 分支有正确处理，但 content-length 分支仍有问题
- **改善证据**:
  - src/http/body.ts:110-121 chunked 超限分支有正确的 cleanup() 和 req.resume() 处理
  - src/http/body.ts:82-84 content-length 分支仍然直接抛出异常
- **遗留问题**:
  - src/http/body.ts:82-84 检查 content-length 后直接抛出 `createPayloadTooLargeException`
  - 没有像 chunked 分支那样调用 req.resume() 来消费请求体
- **风险**:
  - 如果客户端声明了超大 body 且继续发送数据，server 在返回 413 后仍可能占用 socket/parser 资源
  - 这更偏向资源耗尽风险，不是典型的长期 heap 泄漏，但在攻击流量下会造成内存和连接压力
- **修复建议**:
  - 在 content-length 分支也添加 req.resume() 调用，与 chunked 分支保持一致
  - 或者在捕获 PayloadTooLargeException 的地方统一处理 req.resume()

1. 【已知限制】低风险 - 请求 body parser 会按设计缓存完整的已接受 body
- **当前状态**: 按设计工作，但受 maxInflight 未实现影响
- **证据**:
  - src/http/body.ts:87 保存 rawBodyChunks 数组
  - src/http/body.ts:142 将完整 raw body 进行 Buffer.concat
  - src/http/options.ts:104 默认 maxRequestBytes 为 8_000_000
- **风险**:
  - 这本身不是泄漏，但每个并发请求最多可能占用接近 maxRequestBytes 的 body 内存
  - **因为 maxInflight 尚未执行（参见问题 #3），高并发下这个问题会被显著放大**
- **建议**:
  - **优先实现 maxInflight（参见问题 #3 的建议）**
  - 对大文件上传提供 streaming API
  - 在资源受限部署中降低默认 maxRequestBytes

1. 【已知限制】低风险 - Router handler Map 只受 dynamic directory 文件数量约束
- **当前状态**: 按设计工作，受目录删除残留问题影响
- **证据**:
  - src/router/index.ts:11 创建 handlers Map
  - src/watcher/base.ts:20-53 递归注册所有文件
- **风险**:
  - 这是文件系统路由的预期行为，但如果 dynamic directory 被当作无限上传目录使用，route/static handler 条目也会无上限增长
  - **如果删除事件遗漏（参见问题 #5），上述目录删除残留问题会进一步放大该风险**
- **建议**:
  - 文档明确说明 dir 不应直接作为无限上传目录，除非合理配置 exclude/apiExts
  - 增加可选 route 数量上限
  - **优先解决问题 #5 的目录删除残留问题**

## 新发现的问题

### ⚠️ 新问题 - middleware 执行过程中缺少资源清理
- **证据**:
  - src/cluster/server.ts:111-136 执行 middleware 循环，但如果 middleware 抛出异常或超时，没有清理已执行的 middleware 状态
  - 没有机制回滚或清理已经执行的 middleware 副作用
- **风险**:
  - 如果 middleware 在执行过程中创建了资源（如临时文件、数据库事务），后续 middleware 失败时这些资源可能无法被清理
- **建议**:
  - 考虑实现 middleware 的事务性或提供 cleanup 机制
  - 或在文档中明确说明 middleware 应该自行处理异常清理
